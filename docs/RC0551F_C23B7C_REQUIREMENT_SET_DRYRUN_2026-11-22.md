## Authoritative source and version mapping

- `IntakeRequirementSet` belongs to an immutable source `IntakeScopeRevision` and one owning `ProjectIntake`. Each set is its own immutable versioned record, with `version > 0` and unique `(project_intake_id,version)`. Migration `20261120204500` intentionally removed uniqueness of `(project_intake_id,intake_scope_revision_id)` to allow **multiple requirement-set review versions per one scope snapshot**. The two version numbers are independent.
- Enqueue is `DomainOutboxEvent.enqueue_requirement_revision!`: `source_type=IntakeRequirementSet`, `source_id=set.id`, `source_version=set.version`, `kind=requirements_saved`, `occurred_at=set.created_at`, `workspace_id=set.project_intake.workspace_id`. The existing `Activity::Recorder` records key `IntakeRequirementSet:<id>:requirements_saved`, subject id/type, kind, `metadata.version=set.version` and occurred_at created time. Neither callback sends external AI.
- Existing low-level Replayer validates source ID/version and owner workspace, but does not independently validate requirement-set ancestry or exact `created_at`. The new dry-run flags lineage/timestamp differences for human review and **DOES NOT CHANGE** the low-level Replayer or authorize replay.

## Read-only service

[Functional SHA `d684873`](https://github.com/TheGor-365/rails_calendar/commit/d684873a25fffa48621e198c6f1c19a346992f42) adds `app/services/domain_outbox/requirement_set_backfill_dry_run.rb` and `test/services/domain_outbox/requirement_set_backfill_dry_run_test.rb`. `preview(owner:,limit:,cursor:)` uses verified owner/workspace and joins `IntakeRequirementSet -> ProjectIntake` plus `LEFT JOIN IntakeScopeRevision` to retain and count orphan/foreign lineage as `ineligible_sources` instead of silently dropping. It plucks only numeric IDs, versions and timestamps; **never loads `requirements`, `answers`, titles or client content**.

Eligibility: positive `IntakeRequirementSet.version`, linked source scope row exists, its project_intake_id equals the set's project_intake_id, source version positive and source timestamp not later than set timestamp. One origin scope revision may legitimately lead to many requirement-set review versions; no assumption that their version numbers match. Only uniquely matching outbox source version/kind/occurred_at and exact ActivityEvent key/subject/kind/occurred_at/metadata.version count as `already_indexed`. Wrong envelope/projection is `inconsistent_records`, invalid source lineage `ineligible_sources`, never auto-backfilled. No per-statement JSON content or business requirement correctness is asserted.

Bounds and output: strict integer 1..25 source sets/page; at most 250 sets per cursor chain; initial max ID ceiling, keyset progression `id > after_id`, 15-minute AES-256-GCM encrypted owner/workspace/source-type-scoped cursor. Returns only `source_type`, `inspected`, six counts (`already_indexed`, `projection_only`, `envelope_only`, `missing_both`, `inconsistent_records`, `ineligible_sources`), `has_more`, `scan_budget_exhausted`, opaque `next_cursor`. No IDs, source bodies or privacy-sensitive fields leave service. No cross-page consistent snapshot guarantee.

Tests use fictional ephemeral CI database fixtures with a requirement set of versions 1..4 referring to the SAME scope-revision version 1; validate four presence combinations, ineligible foreign-source lineage, outbox source_version and activity metadata version drift, occurred_at drift, owner/client/guest denial, tampered/foreign-family cursor, page-limit and total-budget fail closed, and no writes by the preview itself. Synthetic fixture setup may create, update and delete ONLY its own artificial CI records. No local/production scans, DB writes, routes, job/scheduler, replay or provider calls.
